This section is basically explaining **how to make an AI agent handle work that is bigger than one context window**.

The key idea is:

> **Don't make the agent do a huge task in one session. Define the destination with a Spec, then divide the journey into Tickets.**

### 1. Why context size matters

Think of an agent's context window like its **working memory**.

For a small task:

```text
Task
 ↓
One session
 ↓
Understand → Code → Test → Finish
```

The whole task fits comfortably inside the **smart zone**.

But imagine:

> "Refactor our entire application from REST controllers → service layer → repositories → database → tests."

That's too much.

If you keep everything in one session:

```text
┌─────────────────────────────────────────────┐
│ Context Window                              │
│                                             │
│ Smart Zone          Dumb Zone               │
│ ████████████████████░░░░░░░░░░░░░░░░░░░░  │
│                         ↑                   │
│                    quality degrades         │
└─────────────────────────────────────────────┘
```

The agent starts with a lot of useful context, but as the conversation grows, older information becomes harder for the model to use effectively.

So instead:

```text
Big Task
   │
   ├── Ticket 1 → Session 1
   ├── Ticket 2 → Session 2
   ├── Ticket 3 → Session 3
   └── Ticket 4 → Session 4
```

Each session gets a **small, manageable piece**.

---

# 2. The two documents solve two different problems

This is the most important part of the lesson.

You need:

```text
SPEC
 ↓
Where are we going?

TICKETS
 ↓
How do we get there?
```

### Spec = Destination

The spec describes the **final state you want**.

For example:

> "Migrate the application from MySQL to PostgreSQL."

The spec might define:

* PostgreSQL becomes the production database
* all repositories work with PostgreSQL
* migrations are implemented
* existing functionality continues to work
* tests pass
* performance requirements are maintained
* MySQL-specific code is removed

The spec answers:

> **"What does success look like?"**

And importantly, **every session can refer back to it**.

---

### Ticket = One piece of the journey

The ticket takes a small part of the spec and makes it executable within one session.

For example:

```text
Ticket 1
Create PostgreSQL schema and migration setup

Ticket 2
Migrate UserRepository

Ticket 3
Migrate OrderRepository

Ticket 4
Migrate PaymentRepository

Ticket 5
Update integration tests

Ticket 6
Remove MySQL-specific code
```

Each ticket should ideally be small enough that:

```text
Ticket
   ↓
One session
   ↓
Understand
Implement
Test
Finish
```

---

# 3. The important distinction

A very simple way to remember it:

|           | Spec                         | Ticket                  |
| --------- | ---------------------------- | ----------------------- |
| Purpose   | Define destination           | Define one step         |
| Scope     | Entire project               | One chunk               |
| Answers   | **What are we building?**    | **What do we do now?**  |
| Lifetime  | Entire multi-session project | Usually one session     |
| Passed to | Every session                | Relevant session        |
| Success   | Final project outcome        | Completion of one chunk |

So:

> **Spec = destination**
> **Ticket = journey**

That's why the quiz answer is **"The spec is the destination; each ticket is one leg of the journey."**

---

# 4. Why Spec alone isn't enough

Suppose you give the agent:

```text
SPEC:
Migrate the entire application from MySQL to PostgreSQL.
```

The agent knows **where to end up**, but doesn't necessarily know how to divide the work.

It might start doing:

```text
UserRepository
↓
OrderRepository
↓
PaymentRepository
↓
Database config
↓
Tests
↓
...
```

And eventually the context becomes huge.

Instead, you explicitly create:

```text
SPEC
│
├── Ticket 1
├── Ticket 2
├── Ticket 3
├── Ticket 4
└── Ticket 5
```

Now every session has a bounded problem.

---

# 5. The really powerful part: sessions become independent

Imagine Ticket 3 is:

> Migrate OrderRepository to PostgreSQL.

Session 3 doesn't need the entire history of Sessions 1 and 2.

It needs:

```text
Global destination
        ↓
      SPEC
        +
Current work
        ↓
   TICKET 3
        +
Current codebase
        ↓
Implementation
```

So the new agent session can quickly understand:

> "We're migrating the application to PostgreSQL. My specific responsibility is OrderRepository. I need to implement it and make sure the tests pass."

This is much better than saying:

> "Here's our 80,000-token conversation. Figure out where we are."

---

# 6. Think of it like software project management

This isn't actually a new programming concept.

It's very similar to traditional development:

```text
Project Goal
     ↓
Requirements / Spec
     ↓
Epic
     ↓
Tickets
     ↓
Developer implements ticket
     ↓
PR
     ↓
Next ticket
```

The difference is that now **the developer might be an AI agent**, and context management becomes extremely important.

---

# 7. One subtle but important point

The tickets should **not simply be arbitrary chunks of files**.

You want chunks that represent **meaningful units of work**.

Bad:

```text
Ticket 1:
Modify files A, B and C.

Ticket 2:
Modify files D, E and F.
```

Better:

```text
Ticket 1:
Introduce new repository interface.

Ticket 2:
Implement PostgreSQL repository.

Ticket 3:
Migrate service layer to new repository.

Ticket 4:
Update integration tests.
```

Why?

Because each ticket should leave the codebase in a **coherent state**.

Ideally:

```text
Ticket 1 → working state
Ticket 2 → working state
Ticket 3 → working state
Ticket 4 → working state
```

rather than:

```text
Ticket 1 → half broken
Ticket 2 → more broken
Ticket 3 → finally works
```

# 8. The overall mental model

I would remember this section with this diagram:

```text
                 MASSIVE TASK
                      │
                      ▼
                    SPEC
             "Where are we going?"
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       Ticket 1    Ticket 2    Ticket 3 ...
          │           │           │
          ▼           ▼           ▼
       Session 1   Session 2   Session 3
          │           │           │
          ▼           ▼           ▼
       Smart Zone Smart Zone Smart Zone
          │           │           │
          └───────────┴───────────┘
                      │
                      ▼
                 Final System
                      │
                      ▼
              Review against SPEC
```

And that last step is important:

**The spec isn't only used at the beginning.**

At the end you ask:

> "Did we actually reach the destination described by the spec?"

So you have:

**Spec → plan → tickets → implementation → review against spec**

That's the fundamental pattern this lesson is teaching.
