
The key thing to understand in this lesson is **what `/to-spec` is doing and why it comes after `/grill-me`**:

### The important distinction

Think of the workflow as:

**Conversation → Spec → Tickets → Implementation**

The `/grill-me` skill is used to **discover and make decisions**.

The `/to-spec` skill is used to **capture those decisions as a durable destination document**.

So `/to-spec` is **not supposed to figure out the feature from scratch**. It assumes the conversation already contains the decisions produced by the grilling session.

For the Instructor Analytics example, the conversation might establish things like:

> We want instructors to see enrolled students, earnings, completion rates, and quiz performance.

But grilling should push further:

* What exactly counts as an enrolled student?
* Are earnings lifetime or for a selected period?
* What date ranges are supported?
* How should completion rate be calculated?
* What happens for courses with no quiz?
* Should analytics be per-course or across all courses?
* Does an instructor see only their own courses?
* Do we need charts or just metrics?
* What is explicitly **not** included?

After those decisions exist in the conversation, `/to-spec` turns them into something much more structured.

### Why the spec has both user stories and implementation decisions

These two sections serve different purposes.

**User stories describe behavior/value:**

> As an instructor, I want to see my course completion rate so that I can understand how effectively students are progressing.

They answer:

**"What should the system allow the user to do?"**

**Implementation decisions describe the technical shape:**

> Analytics should be calculated at both instructor-level and course-level. Earnings should be based on completed purchases rather than course list price.

They answer:

**"What decisions have we already made about how this should work?"**

The spec therefore sits between **product requirements and implementation**.

### One particularly important rule

The lesson explicitly says:

> **Do NOT include specific file paths or code snippets.**

That's intentional.

A spec should capture **stable decisions**, not implementation details that can become stale.

For example:

❌ Bad spec:

```text
Modify src/components/InstructorDashboard.tsx
and add getInstructorAnalytics() to analyticsService.ts
```

That couples the destination document to today's code structure.

Better:

> The instructor dashboard should obtain analytics through a dedicated analytics interface that supports instructor-level and course-level metrics.

The agent implementing the ticket can inspect the current codebase and determine the appropriate files.

### Why this is useful for AI coding

This is really a **context-management technique**.

Imagine the feature takes several sessions:

```text
Session 1
    ↓
Grilling
    ↓
Spec
    ↓
Session 2
    ↓
Tickets
    ↓
Session 3
    ↓
Implementation
    ↓
Session 4
    ↓
Review
```

You don't want Session 4 to depend on the model remembering everything from Session 1.

The **spec becomes the persistent source of truth**.

That's the deeper reason the lesson calls the spec a **destination document**.

And the important boundary for this exercise is:

**Don't jump from the spec to implementation.**

The course is deliberately teaching:

**discover → document → later decompose → implement → verify**

rather than asking the coding agent to immediately start writing code.
